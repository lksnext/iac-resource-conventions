# Release Notes — v0.1.0-alpha.1 (draft)

> **Status:** Draft. This is not yet a published release — no package has been published to
> GitHub Packages and no Git tag has been created for this version. See
> [`docs/release-notes/v0.1.0-alpha.0.md`](v0.1.0-alpha.0.md) for the first alpha this one
> follows.

This is the second alpha of `iac-resource-conventions`'s implementation packages:
`@lksnext/iac-conventions-core`, `@lksnext/iac-conventions-catalog`, and
`@lksnext/iac-conventions-cli`, all versioned `0.1.0-alpha.1`. It adds the **Azure
portability slice**: a second, evidence-backed platform slice covering a
representative Terraform-based Azure workload.

## What this alpha adds

- **Nine Azure Resource Definitions** — `azure_resource_group`, `azure_virtual_network`,
  `azure_subnet`, `azure_network_security_group`, `azure_linux_virtual_machine`,
  `azure_key_vault`, `azure_postgresql_flexible_server`, `azure_log_analytics_workspace`, and
  `azure_compute_gallery` — every technical constraint sourced from official Microsoft Learn
  documentation, cited using the same Explicit/Derived evidence-classification convention the
  AWS slice already established (see
  [`packages/catalog/README.md`](../../packages/catalog/README.md) and
  [`docs/architecture/resource-definition-catalog.md#azure-portability-slice`](../architecture/resource-definition-catalog.md#azure-portability-slice)).
- **Three Azure Convention Packs** — `azure-workload-default` (general-purpose,
  hyphen-separated), `azure-workload-compact` (for `azure_key_vault`, whose 24-character
  maximum is too tight for the default pack's full naming component set), and
  `azure-workload-underscore` (for `azure_compute_gallery`, whose naming grammar forbids
  hyphens entirely), implementing three new Specification Artifacts under
  [`specification/convention-packs/`](../../specification/convention-packs/).
- **A second Terraform example**,
  [`examples/terraform/azure-workload/`](../../examples/terraform/azure-workload/), naming a
  representative set of Azure resource types through the same `terraform-external` bridge
  the first (AWS) [`examples/terraform/external/`](../../examples/terraform/external/)
  example uses.
- **Expanded catalog, integration, and CLI test coverage** for every new Resource Definition
  and Convention Pack, including a domain-invalid case (`azure_key_vault` under
  `azure-workload-default`, whose full naming component set exceeds Key Vault's 24-character
  maximum) exercised end-to-end through both `evaluate()` and the CLI.

## What this alpha does not change

- **No Specification concept changed** — no new domain model, schema field, or JSON Schema
  was added or modified; only new Specification Artifacts (concrete Convention Packs) were
  added under `specification/convention-packs/`, consistent with the Specification v1.0 freeze
  (see [`specification/README.md#specification-status`](../../specification/README.md#specification-status)).
- **No core provider logic** — `packages/core` was not modified; all Azure-specific data
  (naming rules, abbreviations, region codes) lives entirely in `packages/catalog`'s
  `ResourceDefinition`/`ConventionPack` values, not in the Reference Evaluator.
- **No native Azure SDK or Terraform `azurerm` provider dependency** — the new Terraform
  example, like the existing AWS one, only evaluates naming conventions locally through the
  `terraform-external` bridge; it never contacts Azure.
- **No new runtime dependency** was added to any package.
- **Maintaining an existing hand-written naming scheme's generated names is explicitly not
  a goal** — see
  [`examples/terraform/azure-workload/README.md`](../../examples/terraform/azure-workload/README.md#migration-notes-preserving-an-existing-hand-written-naming-scheme-is-not-required)
  for migration guidance.

## Known limitations (carried over and Azure-specific)

- **No global name uniqueness verification** — `azure_key_vault` and
  `azure_postgresql_flexible_server` both require globally unique names; this catalog
  documents and validates length/character constraints only, exactly as it already does for
  AWS resources with a global or partition-wide uniqueness scope (see
  [`docs/release-notes/v0.1.0-alpha.0.md#known-limitations`](v0.1.0-alpha.0.md#known-limitations)).
- **`azure_postgresql_flexible_server`'s naming-rule citation is Derived, not Explicit** — the
  Azure Resource Manager naming-rules table lists a general `Microsoft.DBforPostgreSQL/servers`
  rule, not a `flexibleServers`-specific line item; this catalog applies that rule to
  `flexibleServers` by corroboration with the flexible-server quickstart's own example naming,
  not an explicit statement (see the provenance comment in
  `packages/catalog/src/azure/postgresql-flexible-server.ts`).
- **`azure_linux_virtual_machine` is Linux-only** — Windows virtual machines have a materially
  different (15-character) host-name limit and are deliberately not modeled by this entry, the
  same general-purpose-only scoping precedent `aws_s3_bucket` already established.
- **Still no metadata projection, general normalization, truncation, or hashing** — unchanged
  from v0.1.0-alpha.0.
- **Pre-1.0 compatibility is not guaranteed** — this remains an alpha prerelease.
